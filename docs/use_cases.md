# RuntimeXRay Use Cases

RuntimeXRay is designed to answer security questions about compiled applications using evidence collected from:

- the binary;
- runtime execution;
- process memory;
- process relationships;
- runtime resources;
- explicit data-flow relationships.

The key idea is not:

> "Find as many warnings as possible."

It is:

> **Collect evidence that supports a concrete security conclusion.**

This document describes practical use cases that RuntimeXRay can support today, together with examples of where custom detection rules can extend the platform.

---

# 1. Verify binary hardening before release

## Problem

A team produces a Linux binary and wants to verify that expected exploit mitigations are present in the actual compiled artifact.

Source-level build settings are not sufficient evidence because:

- build flags may differ between environments;
- release packaging may use a different toolchain;
- dependencies may alter linker behavior;
- CI configuration may drift.

---

## RuntimeXRay approach

Run:

```bash
runtimexray analyze \
  --min-severity Info \
  ./myapp
```

RuntimeXRay can report:

```text
NX
PIE
RELRO
Stack Canary
```

Example:

```text
NX: Enabled
PIE: Enabled
RELRO: Full
Canary: Enabled
```

---

## Value

This verifies properties of the **actual binary being shipped**.

It can be used as:

- a release gate;
- a packaging check;
- a build-regression detector;
- a binary-review step.

---

# 2. Detect hardening regressions

## Problem

A new release accidentally loses a security property.

For example:

```text
Release N:
RELRO: Full

Release N+1:
RELRO: Partial
```

The source change that caused it may not obviously look security related.

---

## RuntimeXRay approach

Generate structured JSON for each release:

```bash
runtimexray analyze \
  --min-severity Info \
  --json release.json \
  ./myapp
```

A CI system can compare semantic Findings such as:

```text
kind = binary_hardening
attributes.feature
attributes.status
```

---

## Value

Security properties become measurable release artifacts instead of assumptions.

```text

```

Examples:


---

## Value

# 10. Correlate a sensitive value from file to network output

## Problem

Finding a secret in memory is useful.

Finding a network send is useful.

But those two observations alone do not prove that the secret was sent.

---

## RuntimeXRay approach

Enable memory correlation:

```bash
runtimexray trace \
  --scan-memory \
  ./myapp
```

RuntimeXRay can correlate:

```text
source file
    ↓
read / receive
    ↓
same exact sensitive-value fingerprint
    ↓
independent process-memory observation
    ↓
write / send
    ↓
socket destination
```

---

## Example Finding

```text
Sensitive object observed from file to socket

source_file=/tmp/credential.txt
socket_destination=10.0.0.5:443
fingerprint=hmac-sha256:...
confidence=exact-fingerprint-match
```

---

## Value

This is stronger than independent alerts because the Finding connects multiple evidence points.

It can answer:

> Was the same exact sensitive value observed at the input, memory, and network-output boundaries?

---

## Limitation

This still does not automatically prove:

- malicious intent;
- successful remote receipt;
- attacker ownership of the destination;
- compromise.

---

# 11. Track a sensitive value across processes

## Problem

Modern applications often use multi-process pipelines.

A sensitive value may move through several processes before reaching its final consumer.

A list of independent events does not show that relationship.

---

## RuntimeXRay approach

RuntimeXRay models pipe resources and explicit `DataFlow` edges.

Example:

```text
Process A
    │
    │ write(pipe 1)
    ▼
Process B
    │
    │ read(pipe 1)
    │
    │ write(pipe 2)
    ▼
Process C
```

The same exact sensitive-value fingerprint can be correlated across explicit pipe boundaries.

---

## Finding

Current higher-level Finding:

```text
Sensitive value observed across a cross-process pipe chain
```

with attributes such as:

```text
fingerprint
boundary_count
session_count
resource_ids
process_instance_ids
sessions
confidence
```

---

## Value

This is useful for architectures containing:

- helper processes;
- CLI pipelines;
- privilege-separated services;
- process workers;
- wrappers;
- fork/exec chains.

---

```bash
  --report /dev/null \
```

```text

secret_type
```

## Value

# 21. Build a custom organization policy rule

RuntimeXRay's current extension point is:

```text
IDetectionRule
```

A company can integrate a custom rule that inspects the `LineageGraph`.

---

## Example use case

Acme applications must never access:

```text
/opt/acme/master-credentials/
```

---

## Example Primary rule

```cpp
#include "idetection_rule.hpp"

class AcmeCredentialPathRule
    : public runtimexray::IDetectionRule
{
public:
    std::string id() const override
    {
        return
            "acme.master_credential_access";
    }

    std::string description() const override
    {
        return
            "Detects access to Acme "
            "master credential paths";
    }

    runtimexray::DetectionStage
    stage() const override
    {
        return
            runtimexray::DetectionStage::Primary;
    }

    runtimexray::FindingList detect(
        const runtimexray::DetectionContext&
            context) const override
    {
        runtimexray::FindingList result;

        for (const auto& observation :
             context.graph.observations) {

            if (observation.type !=
                runtimexray::ObservationType::Event) {
                continue;
            }

            if (observation.syscall_name != "open" &&
                observation.syscall_name != "openat") {
                continue;
            }

            if (observation.source.find(
                    "/opt/acme/master-credentials/")
                == std::string::npos) {
                continue;
            }

            runtimexray::Finding finding;

            finding.kind =
                "acme_policy_violation";

            finding.severity =
                runtimexray::FindingSeverity::Critical;

            finding.title =
                "Master credential path accessed";

            finding.summary =
                "Process attempted to access "
                "an Acme master credential path.";

            finding.attributes["path"] =
                observation.source;

            finding.attributes["return_value"] =
                static_cast<int64_t>(
                    observation.return_value);

            if (observation.seq != 0) {
                finding
                    .evidence_observation_seqs
                    .push_back(
                        observation.seq);
            }

            result.push_back(
                std::move(finding));
        }

        return result;
    }
};
```

---

## Value

RuntimeXRay can become organization-aware without hard-coding every policy into the upstream project.

# 24. Custom secret classification

## Problem

An organization uses credential formats that generic secret detection does not recognize.

Example:

```text
ACME-PROD-CRED-...
```

---

## Current architectural consideration

Secret extraction currently happens before `SensitiveDataPresenceRule`.

A custom detection rule can only consume evidence that collectors have already produced.

Therefore supporting a new secret format may require:

```text
collector / secret-extractor extension
+
detection rule
```

rather than only a new rule.

---

## Important principle

Detection rules should not pretend that data was collected when it was not.

# 30. Why semantic Findings matter

Backend events may differ in implementation detail.

A useful comparison asks:

```text
Did both backends detect the same supported security condition?
```

not:

```text
Did both produce exactly the same internal event stream?
```

This is one reason RuntimeXRay separates collection from detection.

# 37. What makes a good RuntimeXRay use case?

A strong RuntimeXRay use case has:

```text
security question
        ↓
observable evidence
        ↓
supported relationship
        ↓
structured Finding
```

Example:

```text
Question:
Did the same credential cross two process boundaries?

Evidence:
pipe writes + reads
resource identity
matching fingerprint
process identities

Relationship:
explicit DataFlow edges

Finding:
sensitive_value_cross_process_pipe_chain
```

---

# 38. What makes a weak use case?

Weak:

```text
Find the word "password"
somewhere
+
find a network send
somewhere
=
password exfiltration
```

The observations may be unrelated.

RuntimeXRay should avoid conclusions that depend only on coincidence.

---

# 39. Evidence hierarchy

Not all correlation evidence is equally strong.

A useful conceptual hierarchy is:

```text
same execution
      ↓
same process
      ↓
same exact fingerprint
      ↓
same resource
      ↓
explicit graph relationship
```

The more explicit the relationship, the stronger the supported conclusion.

This is not a numeric confidence model; it is a design principle.

---

# 40. Use cases not currently supported well

RuntimeXRay does not yet provide strong support for:

- arbitrary function-level tracing;
- universal taint tracking;
- exact secret lifetime measurement;
- arbitrary memory-copy causality;
- encrypted/transformed-value lineage;
- full shared-memory dataflow;
- complete network protocol reconstruction;
- malware classification;
- exploitability proof.

These belong to future work or to other specialized tools.

---

Each should use explicit resource identity where possible.

# 46. Using RuntimeXRay with other security tools

RuntimeXRay is complementary to:

```text
SAST
dependency scanners
checksec
strace
Ghidra
IDA
Frida
EDR
sandbox systems
```

Examples:

```text
SAST:
What may happen?

RuntimeXRay:
What did happen in this execution?

Ghidra:
How does this binary implement it?

RuntimeXRay:
Which behavior should I investigate first?
```

# 47. Evidence-first AI use case

AI explanation is a planned presentation capability.

A safe future workflow is:

```text
Lineage evidence
       ↓
Detection rules
       ↓
Structured Findings
       ↓
Narrative
       ↓
Optional AI explanation
```

The AI should explain already established evidence.

It should not invent:

- observations;
- relationships;
- Findings;
- confidence.

---

# 48. Raw secrets and AI

Raw secret values should not be sent to external AI providers by default.

If future AI integration exists, the default input should be:

```text
redacted evidence
fingerprints
metadata
structured Findings
```

not raw memory chunks.

---

# 49. Custom rules vs new collectors

Not every new use case can be implemented only as a detection rule.

If the necessary evidence does not exist in the `LineageGraph`, a new collector or collector enhancement may be required.

The correct order is:

```text
Need new fact?
    ↓
improve collection

Need new conclusion from existing facts?
    ↓
add detection rule
```

---

# 50. Example: credit-card detection

Suppose an organization wants to detect payment-card numbers in memory.

If RuntimeXRay does not currently classify such values as secret observations, the correct architecture is not to hide raw memory scanning inside a detection rule.

Instead:

```text
Memory collector
      ↓
card-number extraction/classification
      ↓
Data Observation
      ↓
Detection rule
      ↓
Finding
```

This preserves separation between collection and security conclusion.

---

# 51. Example: custom IoC matching

If an organization wants to detect a known string or indicator in collected data, it must first decide whether that indicator is:

```text
raw evidence classification
```

or:

```text
security conclusion
```

If raw bytes must be newly inspected, that belongs in collection/extraction.

If existing observations are already sufficient, a rule can derive the Finding.

---

# 52. Avoid putting external network calls inside rules

A rule should not normally perform:

```text
HTTP lookup
LLM request
threat-intelligence API call
```

during `detect()`.

Reasons include:

- non-deterministic results;
- latency;
- privacy;
- secret leakage;
- CI instability;
- dependency on external services.

External enrichment should be a separate layer.

---

# 53. Evidence portability

Structured JSON makes RuntimeXRay evidence reusable.

One analysis can feed:

```text
CI policy
security review
visualization
report comparison
external enrichment
human investigation
```

without rerunning detection differently for each consumer.

---

# 54. Product direction

The most valuable RuntimeXRay use cases are those where several weak observations become one stronger evidence-backed result.

For example:

```text
Weak:
secret found in memory

Weak:
network send happened

Strong:
same exact sensitive value observed
at input, independently in memory,
and at a socket-bound output
```

or:

```text
Weak:
same secret appears in 3 processes

Strong:
same exact sensitive value traversed
two explicit pipe DataFlow boundaries
across three execution sessions
```

That difference is the core value of lineage.

---

# 55. Summary

RuntimeXRay is useful when the security question can be answered from observable properties of:

- the binary;
- the running process;
- memory;
- files;
- network operations;
- process relationships;
- runtime resources;
- sensitive-value identity.

Current high-value use cases include:

- binary hardening verification;
- dangerous API review;
- sensitive file-access detection;
- network-service observation;
- memory-secret discovery;
- file-to-socket sensitive-value correlation;
- cross-process pipe-chain correlation;
- release security gating;
- binary-only component review;
- AI-generated code verification;
- organization-specific detection rules.

Future value will come from making these evidence chains deeper and more precise — not simply from producing more independent warnings.
